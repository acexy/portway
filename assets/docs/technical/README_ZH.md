# Portway 技术概览

本文档为运维人员和贡献者提供 Portway 的简明公开概览。它描述的是稳定的组件边界和运行时属性，
而非完整的线协议或内部状态机。

## 架构

```text
公网 TCP/UDP/HTTP 流量
          |
          v
  +-----------------+     TCP 或 QUIC      +-----------------+
  |    portwayd     | <------------------> |     portway     |
  |   公共服务端    |   控制 + 数据链路     |   私有客户端    |
  +-----------------+                       +-----------------+
          |                                          |
          | Host/端口 路由                           | 本地 TCP/UDP/HTTP
          v                                          v
       公网用户                                私有服务
```

Portway 将系统分为五个职责：

- **传输层** 通过 TCP 或 QUIC 建立认证的客户端-服务端连接。
- **控制平面** 负责客户端身份、代理注册、心跳、恢复和数据链路请求。
- **数据平面** 承载独立的逻辑流，用于代理流量传输。
- **代理运行时** 将公共 TCP/UDP 端口或 HTTP 域名映射到已认证的客户端注册信息。
- **安全控制** 校验配置、认证连接并执行来源地址策略。

代理层不依赖某一种具体的客户端-服务端传输方式。因此，一条公网 TCP 连接可以通过
TCP 或 QUIC 传递到客户端，而无需更改公共协议或私有服务。

## 注册与身份

服务端可以同时接受 Shared、Governed 和 Managed 认证记录。Token 选择服务端
记录和模式。Shared 客户端使用运行时 ClientID 标识资源归属，Governed 和
Managed 客户端还必须在注册 Session 前声明与独立 Token 绑定的 ClientID。

Shared 和 Governed 客户端将完整期望代理集合作为一次注册操作发送。Governed
声明还受到服务端代理类型、端口、域名和配额规则约束。Managed 客户端从服务端
接收完整代理配置，不能注册替代集合。

新 Session 只有完成对应模式的初始配置后才具备恢复资格：Shared 和 Governed
必须完成非空代理注册，Managed 必须完成首次 Prepare/Activate。初始化失败时
服务端直接删除新 Session，不为其保留恢复窗口。

服务端在对外发布前校验完整集合。如果任一代理与现有端口、域名或规则冲突，
整个操作失败，不会暴露部分状态。模式选择和配置示例见
[多模式认证与配置控制](../authentication/README_ZH.md)。

短暂的传输中断可以在有界窗口内恢复已认证的会话。连接代数（generation）机制可防止旧连接在新连接已被接受后继续获取资源所有权。

## TCP 代理

对于每个被接受的公网 TCP 连接，服务端会向所属客户端请求一条数据链路。
客户端连接到配置的本地 IP 和端口，然后双向中继字节流。

Portway 保留 TCP 流语义，包括半关闭行为。公网监听器和活跃链路均具有显式的资源归属和取消路径。

## HTTP 与 HTTPS 代理

服务端持有可选的 HTTP 与 HTTPS 公网 Listener，并根据已验证的规范化域名注册
进行请求路由。HTTPS TLS 在 `portwayd` 终止，本地回源协议固定为 HTTP。

HTTP 转发使用 Go 标准 HTTP 服务端和反向代理实现。后端连接会尽可能复用，
而非为每个请求创建新的隧道。流式响应和 HTTP/1.1 Upgrade 连接通过认证的客户端链路保持流式传输。

两个入口共用域名注册表和容量限制。HTTPS 使用一个可原子热更新的证书对。
HTTP/HTTPS 都会在域名路由前执行 socket 或可信 Header 来源 IP 拒绝规则。

本地应用程序接收的是普通的 HTTP 请求，无需实现 Portway 帧封装、认证或会话行为。

## UDP 代理

公网 UDP 数据报按代理绑定和访问者地址分组成有界关联。每个关联持有一条认证的数据链路和一个已连接的本地 UDP 套接字，
确保响应返回到正确的访问者。

数据报边界通过有界二进制帧保留。TCP 传输为每个关联使用独立的 RoleData 连接，
而 QUIC 传输则使用独立的双向流。这将流的队头阻塞限制在单个访问者范围内。
队列饱和时会丢弃最新的数据报，有界写入超时仅关闭拥塞的关联。

全局、客户端、代理、来源 IP、待处理、创建速率、数据报大小、队列和内存限制均经过编译时的硬边界校验。

## 传输选择

### TCP

TCP 传输使用 Portway 应用认证和认证加密通道。控制角色和数据角色共享一个监听器，
并在进入各自运行时路径之前进行显式校验。

### QUIC

QUIC 传输使用 TLS 1.3 作为传输安全层，并使用 Portway Token 认证作为应用身份验证。
多个 Portway 流可以共享一个 QUIC 连接，同时保持独立的逻辑归属。

更改所选传输方式不会改变已注册代理的语义。

## 可靠性模型

Portway 的设计围绕以下原则：

- 父子上下文取消传播；
- 阻塞网络操作的截止时间；
- 幂等的资源关闭；
- 有界队列、映射表、待处理链路和并发数；
- 原子化代理发布；
- 显式的永久性和可重试连接错误分类；
- 有界优雅关闭和会话恢复。

认证失败、无效凭据、证书验证错误以及已知的传输不匹配均被视为永久性客户端错误，
不会无限重试。

## 运维边界

Portway 目前针对单运维人员管理的服务端进行优化，而非分布式多租户控制平面。
高可用性、共享集群状态、Web 仪表板和动态插件均在当前范围之外。

应用层控制在补充操作系统的同时，不能替代操作系统、云平台或上游网络策略。
