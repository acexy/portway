# Portway 安全性

Portway 旨在通过认证的公共网关暴露私有服务。运维人员仍需负责主机安全、网络策略、
凭据处理以及通过隧道暴露的应用程序的安全。

## 支持的安全模型

- 每种客户端-服务端传输都需要 Portway Token 认证。
- TCP 传输建立认证加密的应用通道。
- QUIC 传输需要 TLS 1.3 证书验证，并且仍然执行 Portway Token 认证。
- 公网 HTTPS 在 `portwayd` 使用 TLS 1.2 或更高版本终止，并使用独立配置的
  SNI 证书集合。
- Portway 不支持明文传输或自动降级到较低安全模式。
- 无效认证、畸形配置和无效的可信来源头均故障关闭（fail-closed）。

服务端可同时配置一个 Shared Token，以及分别拥有独立 Token 的 Governed 和
Managed 客户端记录。同一服务端内所有 Token 必须全局唯一，并包含大于 32 个
UTF-8 字符；强烈建议使用自动生成的 256-bit 随机值。请将每个 Token 视为长期凭据。

认证失败按规范化来源 IP 限速，且服务端状态内存有界。该机制是应用安全边界，
不能替代上游或内核级拒绝服务防护。

## 凭据处理

- 切勿将真实的 Token、私钥或生产环境证书提交到版本控制中。
- 请勿直接在命令行上传递凭据。
- 限制私钥和配置文件权限。
- 使用密钥管理器或受保护的配置部署机制。
- 怀疑凭据泄露后请立即轮换。
- 在可行的情况下，将内部 CA 私钥离线保管。
- 仅向客户端分发 CA 证书，绝不分发 CA 私钥。

`portwayd` 在缺少 Token 时可能会生成一个并在启动时记录一次，以便运维人员配置客户端。
请相应地保护启动日志。显式配置的 Token 不会被记录。

## QUIC 证书

客户端使用操作系统信任存储；配置 CA 文件后则仅使用该 CA 捆绑包验证服务端证书。
配置的服务端名称必须与证书 SAN 匹配。

`portwayd gen cert` 主要用于需要小型内部 CA 的私有部署。生成的证书材料
仍必须遵循生产环境凭据控制规范进行保护、备份、轮换和分发。

## 公网 HTTPS 证书

公网 HTTPS 根据 SNI 选择显式配置的证书，每个映射名称必须被对应证书 SAN
覆盖。证书内容、路径和映射作为完整集合原子热更新；缺失、过期、无效或不匹配
的候选不会替换当前有效集合。即使引用相同文件，公网 HTTPS 与 QUIC Transport
证书仍具有独立的 TLS 和生命周期语义。

## 来源 IP 过滤

服务端可以加载包含单个地址和 CIDR 前缀的 IPv4/IPv6 拒绝列表。
更新会作为完整快照进行校验，然后才会生效。无效更新将保留上一个有效快照。

该策略覆盖客户端-服务端传输连接和公共代理监听器。对于运行时持有对应连接的已拒绝活跃来源，
其连接会被关闭。

HTTP 和 HTTPS 可以从同一个可信 Header 获取来源地址。字段为空时，HTTPS 在
TLS 握手前检查 socket peer；配置后，两个入口都改用可信 Header，HTTPS 在
TLS 解密后检查。仅当可信上游会删除客户端原值、写入已验证来源链且客户端
无法绕过上游时才能启用。无效地址链会被拒绝。

应用层来源过滤并非 DDoS 防护手段，不能替代防火墙、云安全组、负载均衡器 ACL
或内核数据包过滤器。

## 部署建议

- 仅暴露必要的传输和代理端口。
- 以专用的非特权操作系统账户运行 Portway。
- 通过受控发布保持 Portway 和 Go 运行时的更新。
- 在最早的网络边界处放置高流量过滤。
- 监控认证失败、重连、注册失败和来源策略拒绝事件。
- 在生产部署前测试恢复和回滚流程。
- 对暴露的应用程序施加独立的认证和授权。

## 报告漏洞

请勿在公开 Issue 中披露疑似漏洞。

在可用时，使用此仓库的 GitHub 私有安全建议工作流进行报告。
请包含受影响的版本、部署模式、复现步骤、影响范围以及任何拟议的缓解措施。
请勿包含真实的 Token、私钥、含私钥材料的证书或无关的用户数据。

## 公开文档边界

公开文档描述的是受支持的安全属性和运维人员责任，而非完整的协议规范。
Portway 不将未公开的实现细节视为安全控制手段；认证、密码学验证、
严格校验和故障关闭行为才是安全边界。
